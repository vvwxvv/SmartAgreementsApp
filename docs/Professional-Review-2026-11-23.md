# 专业评审：Agreement 签约应用

> 视角：以外部技术负责人 / 独立开发者的身份，看完代码、文档、三轮改动后的整体判断。
> 不是需求清单，是"我会不会把它交出去、会不会为它负责"的意见。
> 事实基准：2026-11-23 晚，`sourceHash=7cb68384f3bd8c57`，278/278 单元、293 含 Mongo、e2e 60/60 双模式。

---

## 0. 结论先行

**这是一个"内核可信、外壳可疑、定位模糊"的项目。**

- **内核**（约 6 千行）：签署状态机、三层哈希、完成封存、原子 CAS、链接加密存储、PNG 墨迹校验、TSA——
  这些是真正难写对的部分，而且写对了。`packages/agreement` 是我愿意在简历上写的代码。
- **外壳**（约 5.7 万行）：226 个组件、92 个 hooks、4 套 UI 框架、63 个运行时依赖，其中与"签合同"有关的
  不到 10%。这是生成器留下的债务，不是产品。
- **定位**：它现在既不是"内部工具"（成本偏高），也不是"产品"（缺多租户、缺身份、缺法务闭环）。
  必须先选一条路，否则每次迭代都在给两个目标交税。

如果我是接手的技术负责人：**我不会阻止它上线做受控试用，但我会拒绝称它为"电子签名产品"。**
现阶段它是"合同签署与证据留存工具"，这句话必须写进对外文案。

## 2. 产品判断（先说商业，再说技术）

### 2.1 它解决的其实是"证据焦虑"，不是"签字动作"

客户真正的痛点是：**"我发了 Word，对方回了个'收到'，三个月后他说没签过。"**
所以卖点不是"在线签名很酷"，而是：

1. 签的时候对方点开就能签（零注册、零安装）；
2. 签完有一份带时间、来源、内容指纹的 PDF；
3. 事后任何人能用编号在网页上自己核一遍，不用信你。

这三点现在都成立，而且是我实测过成立的（改一个字，`contentMatch=false`）。

### 2.2 但它不能自称"电子签名"，更不能自称"可靠电子签名"

《电子签名法》意义上的"可靠电子签名"要求：签名制作数据专有、签署时仅由本人控制、签署后改动可发现。
本系统满足第三条，**不满足前两条**——没有身份核验，链接谁拿到谁就能签。

两种诚实路线：

- **A. 定位为"签署证据与流程工具"**：不承诺法律效力，只承诺"过程可证"。适合内部/熟客场景，成本最低。
- **B. 接 CA/QTSP（e签宝、法大大这类）做"可靠电子签名"**：实名 + 证书 + 时间戳，法律强度上一个台阶，
  但要资质、要钱、要合规，且会把这套系统降级成"前端壳"。

我的建议：**先 A 站稳，再 B 做增值**。不要在没有实名的情况下用"合法电子签名"做宣传，这是会出事的那种问题。

### 2.3 竞争现实

这个赛道不缺玩家，缺的是"便宜且够用"。大厂按份收费、要企业认证、要实名；
你的差异化只可能在：**极简、私有部署、数据在自己手里、按年买断**。
如果要做成 SaaS 去拼价格，现有架构（单租户、单管理员）撑不住。

### 2.4 产品缺口（按"会不会丢单"排序）

| 缺口 | 影响 | 我的判断 |
|---|---|---|
| ~~没有"拒绝签署 + 理由"~~ | ~~流程断在半路~~ | **已完成**（2026-11-23）：`DECLINED` + 理由，全员停签 |
| 没有附件/附件哈希 | 真实合同大量靠附件（报价单、图纸） | **必做**，且必须进 `contentHash` |

| 没有签署人身份校验 | 链接转发即可代签 | 可选短信/邮箱验证码（表里已有 `codeHash` 字段，没启用） |

## 3. 架构意见

### 3.1 核心与外壳必须分家

现状比例：产品 ≈ 5.9k 行（`packages/agreement` 3.0k + 宿主接线 0.6k + 签署/打印/核验页 1.3k +
签署 API 0.4k + manager 0.6k），其余 ≈ 5.7 万行是生成器遗产。

**我的做法**：

1. `packages/agreement` 独立发私有包（pnpm workspace / 私有 registry），语义化版本；
2. 宿主只保留 4 个薄路由文件 + 一个 600 行的 manager 页；
3. 删掉通用 CRUD 壳（写接口已经 405，读接口也没人用）；
4. 统一到一套样式（现在是 MUI + antd + Radix + 手写 CSS 并存）；
5. `docs/` 与 `design/` 合并成单一事实源，避免两处漂移（这次已经出现过）。

这一步不会让功能变多，但会让"下一次改动"便宜 3 倍以上。

### 3.2 数据层：Mongo 可以留，Prisma 该退场

- 运行时已经用原生 driver，Prisma 只剩 schema 和导入工具——**这是对的**，但 `schema.prisma` 同时扮演
  "文档"和"迁移工具"两个角色，而 `db push` 又没验证过，很尴尬。
- 我的建议：把 schema 降级为参考文档，**明确"索引由脚本管、集合由代码建"**；若要长期演进，
  要么上迁移工具（migrate-mongo），要么换 Postgres（如果未来要多租户/报表）。
- 唯一索引必须有启动检查（已有 `prestart`），这是这类系统的生命线，保持。

### 3.3 领域模型的三个隐患

1. **`signDeadline` 与 `expiresAt` 双字段**：兼容历史可以理解，但它是 bug 温床（延期、哈希版本都绕着它走）。
   新产品不该复制这个设计。
2. **哈希版本混在业务字段里**（`hashV`、`completionHashV`）：版本化思路对，但应该收敛成一个
   `evidenceVersion` 枚举 + 一张兼容表，而不是散落的 if。
3. **没有 tenant/owner**：现在 `createdById` 只有 "operator" / "manager" 两个常量。
   如果要做 SaaS，这是从第一天就该有的字段；补起来会牵扯所有查询。

## 4. 安全意见（含我不同意的部分）

### 4.1 做得好的

- 每个非公开 API 路由内二次鉴权，不迷信中间件；
- 证据三层（内容/签署/完成封存）+ 并发 CAS，这是很多商业产品都没做对的；
- 签名图服务端解析 PNG、反滤波、算墨迹、限解压——这是"防手滑"和"防脚本"的分界线；
- 错误处理上"作废后提交"有专门事件与 409，而不是乐观成功。

### 4.2 我会继续推的

1. ~~**管理入口的认证强度不够**~~：已完成（2026-11-23）——**TOTP 第二因素**（RFC 6238，加密存储、防重放）。
   手势仍是第一因素；Passkey/WebAuthn 可作为下一阶段替换。
2. **Ed25519 证据签名**：现在的哈希是"自证"。有 DB 权限的人可以同时改正文和哈希。
   加上服务端私钥签名 + 事件 `prevHash` 链，才能对外说"连我们自己都改不了"。
3. **限流要出进程**：现在的限流是单进程内存计数。多实例、Serverless 都会失效。
   上线前至少放到 Nginx/Caddy 或云 WAF。
4. **隐私**：IP 属于个人信息（PIPL）。现在 PDF 会永久打印签署 IP，没有保留期说明。
   建议：签署页已只显示本人 IP（这轮改了），下一步加"保留 N 天后脱敏"，并在隐私声明里写清楚。

### 4.3 我不同意的一个决定

**去掉版本控制。** 我理解动机（交付目录没有 `.git`、测试因此挂了），但专业上：
`sourceHash` 能证明"这份构建来自这份源码"，**不能**替代历史、diff、bisect、code review、回滚。
我的建议是保留一个本地/自建仓库（不需要 GitHub），把"能离线构建"和"有版本历史"分开对待。
现在的 `baseline-src-*.tar.gz` 是个折中，但它只是快照，不是历史。

## 5. 可靠性与运维意见

现在的系统在"每天几十份合同"的规模下没问题；一旦上量，四个地方会先疼：

| 瓶颈 | 现象 | 处理 |
|---|---|---|
| PDF 每次现拉 Chromium | 冷启动 1–2 秒，内存尖峰，并发即排队 | 改成队列 + 预热浏览器实例，或转成"渲染服务" |
| TSA 同步 8 秒超时 | 网络差时签署请求被拖慢 | 改成"先签后补时间戳"，异步回填 |
| 单 Mongo 无备份 | 误删/勒索即归零 | 每日快照 + 每月恢复演练（这个必须有证据） |
| 无日志/指标 | 用户说"签不了"，你只能猜 | 请求 ID + 结构化日志 + 三个指标（签署成功率、PDF 失败率、TSA 失败率） |

另外：**Vercel 不适合这个应用**（Serverless 里跑 Chromium 是自找麻烦）。我的选型是
一台小 VPS/容器 + Atlas 副本集，静态资源走 CDN。成本可控，行为可预测。

## 6. 工程质量意见

- **测试**：261 条单元 + 59 项双模式 e2e，对 6 千行核心来说是"够用且偏多"，这是加分项。
  但缺三类：性能（并发签署）、混沌（TSA 挂/Chromium 挂/DB 慢）、视觉回归（PDF 像素）。
- **CI**：现在没有。哪怕不用 Git，也应该有一条"构建→测试→e2e→打快照"的流水线脚本，
  并且**每次产出的 sourceHash 与测试报告绑定**（这点 e2e 已经做了）。
- ~~**代码风格**：`service.js` 1359 行该拆~~ → 已完成（2026-11-23）：纯搬移为
  `service.js`(105) + `domain` + `drafts` + `signing` + `verify` + `renewal` + `parties`。
- **命名**：`src/agreement/service.js` 只是 re-export，`docs/Agreement-ARCHITECTURE.md` 与
  `design/ARCHITECTURE.md` 内容重叠——这类"看起来两套、其实一套"的结构最消耗新人。

## 7. 如果我是负责人：30 / 60 / 90 天

### 0–30 天：把它变成"敢给客户用"的东西
1. 生产环境落地：HTTPS、副本集、索引脚本执行、每日快照 + 一次恢复演练；
2. 网关限流 + 访问日志（应用内限流保留，作为第二层）；
3. 微信真机（iOS/Android）各走一遍，文案改成"建议在浏览器打开"；
4. 拒绝签署 + 证据包导出（JSON+PDF+TSA）；
5. 对外文案去掉"电子签名/合法"字样，改为"签署与证据留存"。

### 30–60 天：把它变成"能维护"的东西
1. 拆包 + 删壳 + 统一 UI（预计代码量降 60%）；
2. 管理认证换成 TOTP/Passkey；
3. Ed25519 签名 + 事件链；
4. CI 流水线 + staging + 回滚脚本；
5. 指标与告警（签署成功率、PDF、TSA）。

### 60–90 天：决定它是"工具"还是"产品"
- 若做产品：多租户、模板库、角色权限、附件、催办、计费；
- 若做工具：私有部署包 + 年费维护，把复杂功能全部砍掉；
- 两条路都别现在同时走。

## 8. 我会立刻做 / 我会拒绝做

**立刻做（按性价比）**
1. 证据包导出（一天）；
2. 拒签流程（两天）；
3. 备份 + 恢复演练（半天，但必须有记录）；
4. TOTP 作为第二因素（两天）；
5. 把 `service.js` 拆成四个文件（半天，纯搬移）。

**拒绝做**
- 在没有实名/CA 的情况下宣传"法律效力"；
- 用"手写签名图"当身份证明（它证明的是"有人画了"，不是"谁画了"）；
- 在这个代码库里再加一套 UI 框架；
- 为了"看起来功能多"而加模板市场/工作流引擎。

## 9. 最后一句

这个项目最值钱的不是界面，是**"每个签名都能被独立重算"** 这件事，以及为此做对的那些脏活：
版本化哈希、封存、并发、作废竞态、PNG 墨迹。它已经比大多数"电子签约 Demo"扎实。

它最危险的地方也不是技术，而是**用词**：一旦对外说成"合法电子签名"，前面所有工程上的诚实都会被
一次纠纷抹掉。把话说小，把证据做厚，这个产品就有活路。
